# 접속 구성 — dev.nado.work와 원격 PC가 어떻게 연결되는가

2026-10-03 기준, 실제 서버와 원격 PC에서 측정·확인한 내용이다 (IMPLEMENTATION-PLAN F-18).

## 한 줄 요약

서버는 공유기 안에 있고 포트포워딩이 없다. 그래도 접속되는 이유는 **서버가 먼저 Cloudflare로 연결을 열어 두고(터널), 바깥 요청이 그 연결을 거꾸로 타고 들어오기 때문**이다. 대신 모든 데이터가 Cloudflare를 거치는데, 한국 회선에서는 그 Cloudflare 접점이 **미국 LA·홍콩**으로 잡혀 원격 화면·제어가 느리다. 이를 피하려고 원격 화면은 브라우저와 PC가 **직접 연결(P2P)** 하도록 했다.

## 1. 구성

```
브라우저(작업대·모바일)                원격 PC (aidev-runner)
        │                                      │
        │ ① https / wss                       │ ① wss (러너가 먼저 연결)
        ▼                                      ▼
   ┌────────────── Cloudflare ──────────────────────┐
   │  접속 지점: LA(LAX)  ──내부망──▶  홍콩(HKG)      │
   └──────────────────────────────────────▲────────┘
                                          ║ ② 터널 (서버가 먼저 열어 둔 연결)
                                          ║
   ┌──────────── 서버 (공유기 안, 포트포워딩 없음) ─────┐
   │  cloudflared 컨테이너                              │
   │    → nginx-proxy-manager 컨테이너 (도메인별 분기)    │
   │      → aidev-auth-gateway 컨테이너                 │
   │         (웹 화면 · API · 러너 허브 · 화면 중계)      │
   └──────────────────────────────────────────────────┘
```

| 구성 요소 | 역할 |
|---|---|
| DNS (Cloudflare 네임서버) | `dev.nado.work` → Cloudflare 주소(프록시 켜짐). 서버의 실제 주소는 드러나지 않는다 |
| Cloudflare | 요청을 받아 터널로 서버에 전달 |
| cloudflared (서버, 컨테이너) | 서버에서 Cloudflare로 나가는 터널을 열어 유지 |
| nginx-proxy-manager (서버, 컨테이너) | 도메인별로 알맞은 서비스에 전달 (termes, supabase 등도 함께 사용) |
| aidev-auth-gateway (서버, 컨테이너) | 웹 화면, API, 러너 연결 관리, 원격 화면 중계 |
| aidev-runner (각 원격 PC) | 서버에 먼저 연결해 두고 명령 실행·화면 캡처·입력 재생 |

## 2. 포트포워딩 없이 접속되는 원리 (터널)

공유기는 **안에서 바깥으로 나가는 연결**은 막지 않고, **바깥에서 들어오는 새 연결**만 막는다. 그래서 들어오는 연결을 만들지 않는다.

1. 서버의 cloudflared가 켜질 때 Cloudflare로 연결을 연다 (안 → 바깥, 공유기 통과).
2. 이 연결을 끊지 않고 계속 유지한다.
3. 누군가 `dev.nado.work`에 접속하면 DNS가 Cloudflare 주소를 알려 주므로 요청은 Cloudflare로 간다.
4. Cloudflare는 그 요청을 서버가 열어 둔 연결 안으로 밀어 넣는다.
5. 응답도 같은 연결로 Cloudflare에 돌아가 브라우저에 전달된다.

```
브라우저 ──▶ Cloudflare ◀══(서버가 미리 열어 둔 연결)══ cloudflared ─ 서버
```

원격 PC의 러너도 같은 원리다. 러너가 `dev.nado.work`로 먼저 연결해 두고, 서버는 그 연결로 명령을 보낸다. 그래서 원격 PC에도 포트포워딩이 필요 없다.

## 3. 왜 느린가 — 거리 때문이다

회선 속도(대역폭)는 문제가 아니다. 데이터가 **물리적으로 먼 길을 돈다.** 한국 통신사 회선이 Cloudflare(무료·일반 요금제 도메인)에 접속하면 서울이 아니라 해외 데이터센터로 연결되는 경우가 흔하고, 측정에서도 그랬다.

원격 화면 한 프레임이 서버를 거칠 때의 길:

```
PC → (LA) → (홍콩) → 서버 → (홍콩) → (LA) → 브라우저
```

마우스·키보드 입력은 이 길을 거꾸로 간다. 그래서 조작하고 결과를 보기까지 약 1초가 걸렸다.

### 측정값 (2026-10-03)

| 구간 | 시간 |
|---|---|
| 서버 안에서 게이트웨이에 직접 요청 | 16 ms |
| Mac → 1.1.1.1 (회선 자체) | ping 5 ms |
| Mac · ally · vm-win → Cloudflare 접속 지점 | LAX, ping 278~288 ms |
| 서버 → Cloudflare 접속 지점 | HKG |
| 같은 상태 확인 요청을 `dev.nado.work`로 | 0.6~4 초 |
| 서버 ↔ 각 PC 러너 명령 왕복 | 330~600 ms |

러너 성능은 원인이 아니었다. ally(1280×720)는 캡처+인코딩이 프레임당 17 ms로 최대 59 fps까지 낼 수 있다.

### 직접 확인하는 법

```bash
curl -s https://dev.nado.work/cdn-cgi/trace | grep -E 'colo|loc'   # colo=LAX 이면 LA를 거침
ping 104.21.76.48                                                  # Cloudflare 접속 지점까지 왕복
```

## 4. 원격 화면의 대책 — 직접 연결(P2P)

러너 0.18.0부터 원격 화면은 브라우저와 PC가 **WebRTC로 직접 연결**한다. 이것도 포트포워딩이 필요 없다.

1. 연결을 맺을 때만 서버를 거친다. 브라우저와 러너가 서로의 주소 후보를 서버를 통해 교환한다.
2. 양쪽이 동시에 상대에게 신호를 보내 각자의 공유기에 길을 뚫는다 (홀펀칭). 주소 후보에는 공유기 바깥에서 보이는 주소도 들어가는데, STUN 서버(`stun.cloudflare.com`)에 물어 알아낸다.
3. 길이 열리면 화면 프레임(0.18.0+)과 마우스·키보드 입력(0.18.1+)이 서버를 거치지 않고 오간다.
4. 직접 연결이 안 되면 자동으로 지금처럼 서버 경유로 동작한다.

```
연결 준비:   브라우저 ──(서버 경유)── 러너          주소 후보 교환
이후:        브라우저 ◀═══ 직접 (UDP) ═══▶ 러너      화면·입력
```

| 상황 | 직접 연결 |
|---|---|
| 브라우저와 PC가 같은 집·사무실 망 | 거의 항상 된다 (vm-win 실측: 프레임 왕복 3 ms, 25 fps) |
| 서로 다른 망 (집 ↔ 회사, 휴대폰 데이터) | 공유기 종류에 따라 되거나 안 된다 |
| 안 될 때 | 서버 경유로 동작 (느린 경로) |

- 직접 연결이 되면 원격 화면 상태줄에 **"직접 연결"**이 표시된다.
- Windows는 관리자 권한으로 실행 중인 러너만 직접 연결을 연다. 처음 한 번 방화벽 규칙 `aidev-runner-p2p`를 스스로 추가한다.
- 게이트웨이 로그에 화면 스트림마다 10초에 한 줄 `[screen] … viewers N direct M`과 직접 연결 전환·실패가 남는다.

## 5. 서버 경유 자체를 빠르게 하려면 (결정 필요)

직접 연결이 안 되는 경우까지 빠르게 하려면 Cloudflare 해외 경유를 피해야 한다.

| 방법 | 포트포워딩 | 비용·수고 | 효과 |
|---|---|---|---|
| 원격 화면용 주소 하나(예: `rt.nado.work`)를 Cloudflare 프록시 없이 서버로 직접 | 필요 (443 → nginx-proxy-manager) | 공유기 설정, Let's Encrypt 인증서 | 국내 경로, 왕복 수십 ms 이하 예상 |
| 국내 클라우드 서버를 중계로 | 불필요 | 서버 비용 | 국내 경로 |
| Tailscale (서버와 Mac은 이미 사용 중) | 불필요 | 기기마다 설치 | 기기 간 직접·국내 경로 |
| TURN 서버 (직접 연결이 막힌 망을 중계) | 필요 (UDP) | 공유기 설정 | 직접 연결 실패 시의 대안 |

## 6. 빠른 주소 (`rt.nado.work`) — 5절 첫 번째 방법

코드는 준비되어 있다 (게이트웨이·화면 페이지, 러너 0.18.2+). `REALTIME_ORIGIN`이 비어 있으면 꺼져 있고, 지금과 똑같이 동작한다.

```
러너 ──wss──▶ rt.nado.work:8443 ─(공유기 포트포워딩)─▶ 서버 nginx-proxy-manager ─▶ 게이트웨이
브라우저 화면 ──wss──▶ 〃                                (Cloudflare를 거치지 않음)
웹 화면·로그인·API ──▶ dev.nado.work (지금처럼 Cloudflare)
```

- 러너: Cloudflare 주소로 들어오면 게이트웨이가 `runner.realtime {url}`로 빠른 주소를 알려 주고, 러너는 그쪽으로 다시 연결한다. 연결이 두 번 연속 실패하면 원래 주소로 돌아가고, 10분 동안은 다시 옮기지 않는다.
- 브라우저: 원격 화면을 열 때 `/api/aidev/realtime`에서 빠른 주소와 2분짜리 접속표를 받는다. 로그인 쿠키는 dev.nado.work 전용이라 접속표가 필요하다. 빠른 주소가 3초 안에 열리지 않으면 원래 주소로 연다. 상태줄에는 "빠른 경로"로 표시된다 (직접 연결이면 "직접 연결").
- 443은 이미 다른 장비(SoftEther VPN)로 포워딩되어 있고 80은 닫혀 있어서, 포트는 8443을 쓰고 인증서는 DNS 인증으로 받는다.

### 켜는 순서

소유자가 할 일:

1. 공유기 포트포워딩: 외부 TCP 8443 → 서버 `192.168.219.55:8443` (nginx-proxy-manager의 HTTPS).
2. Cloudflare DNS: `rt.nado.work` A 레코드 → 서버 공인 IP, 프록시 끔 (DNS only, 회색 구름).
3. nginx-proxy-manager:
   - Proxy Host `rt.nado.work` → `aidev-auth-gateway` : `8080`, Websockets Support 켬.
   - SSL: Let's Encrypt, DNS Challenge (Cloudflare API 토큰, Zone:DNS 편집 권한).

그다음 운영 작업:

4. 바깥에서 확인: `curl https://rt.nado.work:8443/_gateway/health` → `{"status":"ok"}`.
5. 서버 `~/aidev/deploy/.env`에 `AIDEV_REALTIME_ORIGIN=https://rt.nado.work:8443`을 넣고, 게이트웨이 컨테이너를 다시 만든다: `docker compose -p aidev --env-file .env -f docker-compose.yml up -d auth-gateway`.
6. 게이트웨이 로그의 `[runner] … connected`와 러너 로그의 "CDN을 거치지 않는 주소"로 러너가 옮겨 갔는지 확인한다.

### 주의

- 가정용 회선의 공인 IP는 바뀔 수 있다. 바뀌면 빠른 주소는 실패하고, 러너와 화면은 자동으로 Cloudflare 경로로 돌아간다. 오래 쓰려면 DNS를 자동으로 갱신하는 장치(DDNS)를 함께 두어야 한다.
- 서버와 같은 공유기 안에서 접속할 때는 공유기가 자기 공인 IP로 되돌려 보내는 기능(NAT 루프백)을 지원해야 한다. 지원하지 않으면 그 망에서만 원래 경로로 돌아간다.
